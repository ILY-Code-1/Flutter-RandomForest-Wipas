Bagian 1 — Business Requirements Document (BRD)

1.1 Latar Belakang & Tujuan

Perencanaan alokasi manpower warehouse logistik (kurir dan operator) saat ini bertumpu pada projection inbound dari tim Data Intelligence. Dalam praktiknya, terjadi ketidaksesuaian berulang antara projection dan actual inbound yang berdampak pada operasional:

  • Actual > Projection: Memicu backlog (penumpukan paket di warehouse) dan penundaan SLA Delivery.
  • Projection > Actual: Menyebabkan overbudget manpower (pemborosan biaya operasional akibat kurir/operator idle).

Fluktuasi inbound dipengaruhi variabel multi-faktor (campaign, hari libur, payday, pickup request H-1, backlog H-1, dan histori inbound). Metode estimasi konvensional berbasis statistik deskriptif tidak mampu mengolah kompleksitas ini, sehingga dibutuhkan pendekatan Machine Learning ensemble yang tangguh (Amnay & Charani, 2025; Nagendra & Singh, 2023).

Tujuan sistem:

  • Mengurangi risiko backlog dan overbudget manpower melalui prediksi volume inbound yang akurat dan terkalibrasi.
  • Menyediakan evaluasi objektif dan feedback loop otomatis terhadap akurasi projection tim Data Intelligence.
  • Memberikan rekomendasi alokasi manpower secara real-time berbasis konfigurasi kapasitas dinamis (Dynamic Thresholds).
  • Membangun Decision Support System (DSS) berbasis mobile dengan penanganan batch resilience dan idempotency write.
  • Menjadi single source of truth untuk perbandingan projection vs predicted vs actual inbound.

1.4 Kebutuhan Fungsional

M1 Data Collection & Preprocessing
  • FR1.1 Sistem mengumpulkan data historis inbound harian dari database warehouse.
  • FR1.2 Sistem melakukan data cleaning: hapus duplikat, deteksi outlier (metode IQR dengan batas fleksibel).
  • FR1.3 Sistem menangani missing value dengan forward-fill (time-series) dan median (skewed numeric).
  • FR1.4 Sistem encoding fitur boolean (Campaign, Hari Libur, Payday) menjadi 0/1.
  • FR1.5 Sistem memvalidasi rentang nilai non-negative untuk semua fitur numerik dan log ketersediaan data.
M2 Model Training & Evaluation
  • FR2.1 Sistem melakukan pembagian data time-series menggunakan Rolling-Window Cross-Validation (TimeSeriesSplit k-folds) untuk mencegah data leakage dan bias musiman.
  • FR2.2 Sistem melatih model Random Forest Regressor dengan 10 fitur prediktor.
  • FR2.3 Sistem mengevaluasi performa model menggunakan MAE, MSE, RMSE, dan R² pada setiap fold.
  • FR2.4 Sistem menghasilkan feature importance untuk analisis faktor penyebab deviasi volume.
  • FR2.5 Sistem menyimpan model terlatih beserta metadata parameter untuk batch processing harian.
  • FR2.6 Sistem menghitung Model Health Index (MHI) berbasis Rolling MAE 7-Hari untuk mendeteksi Concept Drift.
M3 Prediction Engine & Batch Resilience
  • FR3.1 Sistem menjalankan batch processing harian otomatis pada pukul 23:00 WIB menggunakan data H-1.
  • FR3.2 Sistem menghasilkan prediksi volume inbound untuk H+1.
  • FR3.3 Sistem menggunakan Idempotent Upsert Write Strategy ke Cloud Firestore untuk mencegah duplikasi data jika terjadi retry execution.
  • FR3.4 Sistem mencatat log eksekusi batch (timestamp, status, retry count, execution time).
  • FR3.5 Sistem menerapkan fallback otomatis ke data H-2 jika pemicu data H-1 mengalami keterlambatan pipeline.
M4 Mobile Application
  • FR4.1 User dapat login menggunakan Firebase Authentication (email/password).
  • FR4.2 User dapat memilih tanggal dan melihat detail prediksi inbound H+1.
  • FR4.3 User dapat melihat perbandingan Projection vs Predicted vs Actual (tabel & grafik).
  • FR4.4 User dapat melihat persentase deviasi antara Projection dan Predicted.
  • FR4.5 User dapat melihat estimasi rekomendasi manpower dinamis yang dihitung berdasarkan Dynamic Threshold Configuration.
  • FR4.6 User Admin/Manager dapat mengedit parameter kapasitas operasional (Kapasitas Rider, Driver, Op. Inbound, Op. Outbound) langsung melalui aplikasi.
  • FR4.7 User dapat melihat visualisasi tren inbound dan feature importance.
  • FR4.8 User menerima indikator visual saat sistem mendeteksi Data/Concept Drift (Rolling MAE > 15%).
M5 Authentication & Authorization
  • FR5.1 Sistem menyediakan registrasi akun dengan approval admin.
  • FR5.2 Sistem menyediakan role-based access: Admin, Manajer, Supervisor, Viewer.
  • FR5.3 Sistem menyediakan session management dan auto-logout setelah 24 jam.
  • FR5.4 Sistem menyediakan fitur reset password melalui email.
M6 Data Management
  • FR6.1 Sistem menyimpan hasil prediksi harian di Firestore dengan skema ID dokumen komposit: `pred_{warehouse_id}_{YYYYMMDD}`.
  • FR6.2 Sistem menyimpan histori evaluasi dan log perubahan parameter untuk audit trail.
  • FR6.3 Sistem menyediakan backup otomatis data Firestore setiap minggu.
  • FR6.4 Sistem menyediakan fitur export data ke CSV untuk analisis lebih lanjut.
  • FR6.5 Sistem menyimpan konfigurasi kapasitas operasional pada koleksi `operational_configs` Firestore.

1.6 Arsitektur Sistem

Sistem WIPAS menggunakan pendekatan Daily Resilient Batch Processing & Dynamic Cloud Sync:

  • Python Offline & Execution Batch — script Python mengeksekusi preprocessing, evaluasi TimeSeriesSplit, dan pengerjaan model RF secara batch harian, lalu melakukan `upsert` ke Cloud Firestore menggunakan Deterministic Key.
  • Firebase Cloud Services — Cloud Firestore sebagai penyimpanan real-time, `operational_configs` untuk variabel dinamis, dan Firebase Auth untuk kontrol akses.
  • Flutter Mobile App — membaca hasil prediksi dan parameter operasional secara real-time, menyajikan kalkulasi manpower dinamis, dan memberikan antarmuka manajemen konfigurasi.

Bagian 3 — Algoritma & Formula

3.1 Random Forest Regressor & Time-Series Cross-Validation

Random Forest adalah ensemble learning method yang membangun multiple decision trees berbasis teknik bootstrap aggregation (bagging). Untuk data time-series logistik, pembagian data dilakukan secara bertahap menggunakan TimeSeriesSplit untuk mempertahankan urutan kronologis data.

RF_Prediction = (1/N) × Σ_{k=1}^{N} Tree_k(x) Evaluasi Cross Validation (TimeSeriesSplit k-folds): Fold k: Data Train = [1 ... t_k], Data Validation = [t_k + 1 ... t_k + m] Hyperparameter Utama: n_estimators : 100 - 200 trees max_depth : 10 - 20 min_samples_split : 5 - 10 criterion : squared_error

3.2 Metrik Evaluasi Performa Model & Drift Detection

Mean Absolute Error (MAE)

MAE = (1/n) × Σ |y_i - ŷ_i|

Root Mean Squared Error (RMSE)

RMSE = √[ (1/n) × Σ (y_i - ŷ_i)² ]

R² Score (Coefficient of Determination)

R² = 1 - [ Σ(y_i - ŷ_i)² ] / [ Σ(y_i - ȳ)² ]

Model Health Index (MHI) & Concept Drift Detection

Rolling_MAE_7d = (1/7) × Σ_{d=1}^{7} |Actual_d - Predicted_d| Indikator Drift: Jika Rolling_MAE_7d > 1.15 × Baseline_MAE ==> Trigger Status 'Model Degraded'
Target Kinerja Model: Rolling MAE ≤ 10% · RMSE ≤ 15% · R² ≥ 0.85

3.3 Konversi Prediksi ke Estimasi Manpower Dinamis

Kapasitas kerja operasional dihitung menggunakan parameter fleksibel yang disimpan pada koleksi Firestore `operational_configs`, bukan angka konstan hardcoded.

Formula Estimasi Kurir (Rider & Driver)

Rider (Kebutuhan Armada Motor) = (Predicted_Inbound × Ratio_Rider) / Capacity_Rider Driver (Kebutuhan Armada Mobil) = (Predicted_Inbound × Ratio_Driver) / Capacity_Driver Keterangan Parameter Dinamis (Configurable via App): Ratio_Rider : Proporsi porsi volume kurir motor (Default: 0.70) Ratio_Driver : Proporsi porsi volume kurir mobil (Default: 0.30) Capacity_Rider: Standar penyelesaian paket per rider/hari (Default Config: 350) Capacity_Driver: Standar penyelesaian paket per driver/hari (Default Config: 800)

Formula Estimasi Operator Warehouse

Op. Inbound (Unloading & Receiving) = Predicted_Inbound / Capacity_Op_Inbound Op. Outbound (Sorting & Staging) = Predicted_Inbound / Capacity_Op_Outbound Keterangan Parameter Dinamis (Configurable via App): Capacity_Op_Inbound : Standar penanganan receiving per operator (Default Config: 500) Capacity_Op_Outbound: Standar penanganan sorting per operator (Default Config: 600)

3.4 Perhitungan Deviasi Projection

Deviasi (%) = |Predicted - Projection| / Projection × 100%
Deviasi > 15%: memicu alarm perhatian untuk Manajer Warehouse dan Tim Data Intelligence.

3.5 Feature Importance

Importance(f) = (1/T) × Σ_t Σ_{s ∈ S_t(f)} (n_s / N) × Δi(s,t)

Bagian 4 — Systematic Literature Review (SLR)

4.1 Tujuan SLR

  1. Mengidentifikasi metode ML paling efektif untuk prediksi volume inbound warehouse logistik.
  2. Menganalisis performa Random Forest dibanding metode time-series konvensional dan deep learning (ARIMA, LSTM, XGBoost).
  3. Mengkaji fitur/faktor operasional paling berpengaruh terhadap akurasi prediksi volume.
  4. Mengidentifikasi tantangan penanganan model drift dan penyajian hasil prediksi untuk perencanaan manpower.
  5. Menentukan research gap yang mendasari pentingnya pengembangan Decision Support System (DSS) berbasis mobile.

4.3 Hasil SLR per Tema

Tema 1: Ensemble Learning untuk Supply Chain Forecasting

Amnay & Charani (2025) — Perbandingan ARIMA, ANN, dan RF untuk demand forecasting SCM. RF terbukti sangat kompetitif dibanding ARIMA & ANN, tahan terhadap noise data, dan unggul saat menangani variabel campuran (numerik + katagoris).

Implikasi WIPAS: Random Forest sangat efisien untuk memproses kombinasi variabel numerik (vol) dan boolean (campaign/payday).

Tema 2: Perbandingan Time Series Forecasting Methods & Validation

Ormanda & Ardiansah (2026) — LSTM mencapai akurasi tertinggi (MAPE 0.43%), diikuti Random Forest (MAPE 0.67%), sedangkan ARIMA dan Regresi Linear menunjukkan error >10% pada tren non-linear.

Nagendra & Singh (2023) — Menganalisis bahwa RF & LSTM jauh mengungguli ARIMA pada data ber-fluktuasi tinggi.

Implikasi WIPAS: Meskipun LSTM sedikit lebih presisi, Random Forest dipilih karena efisiensi komputasi batch harian, kemudahan tuning, serta transparansi interpretasi (feature importance). Validation dioptimalkan menggunakan TimeSeriesSplit.

Tema 3: Feature Importance & Model Drift Handling

Mohammed & Mandal (2022) — Menganalisis keunggulan Feature Importance pada RF dalam memberikan penjelasan kausalitas bagi manajemen.

Bai (2024) — Menggarisbawahi bahwa model ML rentan terhadap perubahan pola data eksternal (data drift), sehingga membutuhkan metrik pemantauan kinerja harian/mingguan.

Implikasi WIPAS: Actual H-1 & Pickup H-1 merupakan prediktor terkuat; indikator Rolling MAE diimplementasikan untuk menangani Model Drift.

Tema 4: Workforce Planning & Logistics Optimization

Eichenseer et al. (2024) — ML mampu memprediksi posisi pengiriman untuk alokasi kerja, namun integrasi real-time ke aplikasi operasional lapangan masih menjadi hambatan utama.

Lesmana & Purnomo (2025) — Menggunakan RF untuk estimasi transfer time logistik, namun belum mengaitkan hasil prediksi secara otomatis ke angka kebutuhan manpower.

Implikasi WIPAS: Celah utama literature diatasi oleh WIPAS dengan menghubungkan hasil prediksi volume ke kalkulasi alokasi manpower dinamis berbasis aplikasi mobile Flutter.

4.6 Kesimpulan SLR & Daftar Pustaka

Kesimpulan

  1. Ensemble learning (Random Forest) konsisten menghasilkan performa tinggi pada data supply chain multivariat: robust terhadap outlier, mampu menangani fitur campuran (boolean & numerik), serta memiliki feature importance yang transparan.
  2. TimeSeriesSplit Cross-Validation wajib digunakan menggantikan split acak/statis untuk mencegah data leakage pada evaluasi data logistik.
  3. Fitur paling berpengaruh: Actual Inbound H-1 & Pickup Request H-1 (sangat tinggi), Backlog H-1 & Actual H-2 (tinggi), Campaign/Payday/Hari Libur (sedang–tinggi).
  4. Tantangan utama operasional: Ketiadaan antarmuka real-time dan fleksibilitas konfigurasi kapasitas kerja di lapangan. Model ML di environment notebook tidak berdampak jika tidak dihubungkan ke aplikasi mobile DSS.
  5. Kontribusi Utama WIPAS: Menutup research gap dengan menghadirkan platform end-to-end yang mengintegrasikan prediksi volume, evaluasi projection, perhitungan manpower dinamis, dan jaminan resilience Idempotent Write.

5.3 Prinsip Sistem Terintegrasi & Resilience

  • Single Sign-On & Role Security — Firebase Auth dengan aturan keamanan Firestore berbasis Role untuk melindungi konfigurasi.
  • Idempotent Batch Upsert — Menggunakan kunci dokumen terprediksi (`pred_{wh_id}_{YYYYMMDD}`) agar rerun batch tidak memicu duplikasi record.
  • Dynamic Config Synchronization — Parameter kapasitas kerja disimpan di Cloud Firestore (`operational_configs`) dan di-stream real-time ke aplikasi Flutter.
  • Offline Persistence — Flutter app meng-cache data lokal untuk menjamin keberlanjutan operasional saat koneksi gudang tidak stabil.
  • Model Health & Drift Alerting — Notifikasi otomatis di dashboard saat Rolling MAE 7-Hari melebihi ambang batas toleransi.
  • Human-in-the-Loop Decision Support — Sistem memberikan rekomendasi presisi, namun wewenang penyesuaian akhir tetap pada Manajer Operasional.
